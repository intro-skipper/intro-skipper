# Segments

The plugin's own database, `introskipper-v2.db`, is the source of truth for segments. Jellyfin's MediaSegments table mirrors it per item. This page covers how segments are stored, how every write reaches Jellyfin, and the per-item disable flag. Analysis records and the detection cache are in `docs/analysis.md`.

## Storage

- **One table for every mode.** `Segments` rows are `(Id, ItemId, Type, StartTicks, EndTicks, Source, State, ConfigHash, CreatedAt, UpdatedAt)` under one unique index on `(ItemId, Type, StartTicks, EndTicks)`. An item can hold any number of segments per type, as Jellyfin 12 does, and no mode is special-cased. `CK_Segments_Range` (`EndTicks > StartTicks AND StartTicks >= 0`) makes a valid range a database constraint.
- **Ticks.** Times are `long` ticks, matching Jellyfin's `MediaSegment`, and equality is exact. Seconds exist only at the analyzer and HTTP edges (`TickConversions`).
- **Shared ids.** `Id` is a Guid v7 the plugin generates and the mirror pushes as Jellyfin's segment id, so both databases address a segment by the same Guid. Jellyfin's `MediaSegmentManager` keeps provider-supplied ids. An automatic row whose boundaries survive re-analysis keeps its id. The dependency is deliberately narrow: bulk replace and cleanup are scoped by provider id, never by the shared Guid, and every correlated delete ends in a per-item replace that pushes current truth whatever ids Jellyfin holds. A server that stopped preserving ids would still converge.
- **Provenance.** `SegmentSource` records which analyzer, or the user, produced a row. `Unknown` comes only from the legacy import, and it counts as automatic.
- **Tombstones.** Deleting an automatic segment sets its state to `SegmentState.Suppressed`. The row stays, hidden from normal reads and never mirrored, and blocks automatic re-insertion of any strictly overlapping segment of the same item and mode. User segments are deleted outright. Tombstones survive config-hash cleanup and season reanalysis. The explicit erase operations (mode, season, item) purge them, and restore reactivates one.
- **Migrations.** Schema changes are plain EF migrations on `introskipper-v2.db`, starting from the `InitialCreate` baseline.

## Legacy import

`LegacyDatabaseImporter` reads the old `introskipper.db` once, over a read-only connection. It detects the old schema's shape through `pragma_table_info` and never modifies the file, which stays a rollback path for older plugin versions. The import commits atomically with a `DbImportRecord` marker, and the marker, not the file, answers whether the import ran. Restoring an old `introskipper.db` therefore does not import it again; deleting `introskipper-v2.db` and restarting does. A database rebuild keeps the marker when one exists and writes none otherwise, so a rebuild after a failed startup import leaves the retry and the legacy data reachable.

## Writes

### Automatic writes

`ReplaceAutoSegmentsAsync` is the only analysis write path. It has a single-source form and, for the credits pass, a per-source form over the same core. `AutoSegmentAdmissionPolicy` gates what automation may write, so automation never contradicts recorded human intent:

- An automatic segment is dropped when it strictly overlaps a tombstone or an active user row of the same item and mode. Touching boundaries do not block; one shared tick does.
- Automatic credits are dropped when they overlap an active introduction.

These rules hold at admission only. User writes are admitted unconditionally, and restore and undo do not re-validate, so overlapping rows are legal stored state. The stored state's only invariants are the exact-range unique index and the range check.

### Interactive writes

Every interactive surface commits through `SegmentChange.ApplyAsync`: the plural segments API, the `MediaSegmentsApi` editor contract and the per-item disable toggle. No single-shot user mutator exists on the facade, so nothing writes servable state without recording its projection.

- **Intents and outcomes.** `ApplyAsync` takes a closed `SegmentChangeIntent` (add, replace, update, delete, restore, visibility, editor delete) and returns a typed outcome. `Accepted` carries the affected values and the immediate projection state. `Ignored` means the intent already held: no mutation runs, but a re-projection is still journaled, so retrying an idempotent request heals a diverged mirror. The exception is a target that exists in no state at all, where nothing can have diverged and nothing is journaled. `Rejected` carries a typed reason and journals nothing.
- **One transaction.** `IntroSkipperDatabase.ApplyChangeAsync` commits the mutation, its analysis-record bookkeeping and the projection journal together. Exact-range rows survive in place and keep their ids. Restore re-arms the analysis record and drops the row's `ConfigHash`. An empty replace set deletes, and automatic rows become tombstones.
- **Plural API.** `Episode/{itemId}/Segments` reads and adds; `Episode/{itemId}/Segments/{segmentId}` updates and deletes; `Episode/{itemId}/Segments/{segmentId}/Restore` restores a tombstone. Times are seconds at this edge, and every endpoint requires elevation, the read included, because it returns the unfiltered stored view.
- **Editor contract.** `GET MediaSegmentsApi/{itemId}` returns every active stored segment, including automatic rows of a disabled item, and an `ETag` revision. Tombstones are history and are not returned. `PUT MediaSegmentsApi/{itemId}` takes the complete active image in ticks and requires `If-Match`. A stale revision answers 412 and a missing header 428, so an editor either sends the revision it read or opts out of the check with `*`. The replacement keeps exact ranges and supplied ids where it can and returns the canonical saved rows. Omitted user rows are removed and omitted automatic rows become tombstones. An automatic row at the same range stays automatic, and moving an addressed automatic row makes it the user's. The single-row POST adds and never replaces, so a client that posts one segment at a time cannot overwrite earlier rows of the same type.
- **Editor delete.** `DELETE MediaSegmentsApi/{segmentId}` is the one intent that can delete a Jellyfin row the plugin does not own (`EditorDeleteSegmentIntent`). A plugin row sharing the id is deleted (automatic rows become tombstones) and its Jellyfin twin's delete is journaled with the row's own shape. An id with no plugin row resolves the Jellyfin row lazily, validates that it belongs to the item and type, and matches a plugin counterpart through `IntroSkipperDatabase.FindUncorrelatedCounterpart`: one tick of tolerance and closest wins, or, for a non-commercial mode with nothing in tolerance, the mode's only active row. A retry whose delete is still pending matches the journaled operation first, so the fallback can never claim a segment another request already addressed. A matched counterpart is deleted like any plugin row, which clears that mode's analysis record. With no counterpart, only the foreign row's delete is journaled and the analysis record stays, because a foreign row says nothing about the plugin's own analysis.
- **HTTP mapping.** Controllers only validate and map outcomes through `SegmentChangeHttp`. A change whose projection applied synchronously, and an `Ignored` intent, keep the endpoint's normal response shape. A pending or skipped projection answers 202 with a `SegmentChangeAcceptedResponse`: the change is committed either way. While `UpdateMediaSegments` is off, every accepted write's projection is skipped, so it answers 202. Rejections answer 404 for an absent or foreign-owned target, 412 for a stale editor revision and 400 otherwise. The editor PUT returns its committed revision as an `ETag` on both 200 and 202.

### Maintenance writes

Analyzer and maintenance code calls the facade directly but journals too. Every facade write that changes an item's servable image (`ReplaceAutoSegmentsAsync`, `CleanStaleAutomaticSegmentsAsync`, `EraseItemsAsync`, `DeleteSegmentsByModeAsync`, `ClearCreditsDerivedPreviewsAsync`, `ResetItemsForReanalysisAsync`) enqueues the affected items' markers in its own transaction. Pure bookkeeping, such as analysis records, season state and analyzer actions, journals nothing because Jellyfin serves none of it.

When subtitle detection is enabled, stale automatic rows for Recap and Preview can be retained during cleanup and reanalysis resets. An admitted subtitle match replaces the prior automatic result transactionally; a successful no-match clears the stale subtitle row while the conventional analyzer chain gets the opportunity to refresh its fallback rows. A recap cue after the intro is detection-only unless a later chapter marker supplies its end, so that case preserves the prior subtitle row and leaves the mode eligible for other analyzers. Subtitle output is capped across all embedded streams and sidecars per episode. An incomplete subtitle-source scan leaves the mode retryable even if cues from readable sources produce an admitted candidate; if no candidate is established, prior rows remain intact. A fully rejected candidate preserves standing rows but settles under the current configuration, avoiding repeated scans for a tombstone or conflicting user segment.

A re-analysis that reproduces identical boundaries journals nothing either. A Jellyfin row that was hand-deleted or corrupted therefore stays divergent until a journaled change touches the item, an idempotent interactive request re-asserts it, or Jellyfin's own media segment scan pulls current truth through the provider.

Bulk erases go through `ISegmentEraser`: the dashboard's erase endpoints, the manual scan, the mode erase and the cache cleanup task. Each erase journals the affected items in the same transaction as the delete, then converges only those items through `SegmentChange.ProjectItemsAsync` and leaves anything unfinished to the worker. The detection cache cleanup that can follow is best effort, because the main database is already consistent by then.

## Projection

**The journal stores work, not images.** A marker means "this item's mirror is behind", and applying it re-projects the item's current truth. Replaying stored snapshots instead would force the journal to duplicate every mechanism it sits beside (the servable-image policy, the Jellyfin write transaction, the per-item locking), and could push a stale snapshot over newer truth from a path that does not journal. Re-projecting means a replay can never go stale, markers for one item coalesce, and every crash window costs at most one extra idempotent sync.

- **Journal.** Two tables in the same database. `ProjectionQueue` holds one version-guarded marker per item. `ProjectionExternalOperations` holds durable deletes of validated foreign Jellyfin rows, the only work that cannot be recomputed. Both survive database rebuilds.
- **Apply.** `MediaSegmentMirror.ApplyAsync` is the only write path into Jellyfin's table. It runs the item's journaled foreign-row deletes in order, then pushes every active plugin segment with its id and removes Intro Skipper rows the plugin database no longer holds. When Jellyfin's rows already match, it skips the write, so refreshing unchanged items stays read-only. A journaled delete carries the row's validated type and boundaries, so a row rewritten under its id since validation is left alone. Every write is a no-op while mirroring is off (`IMediaSegmentMirrorPolicy`).
- **One conversion.** `SegmentDtoFactory` builds Jellyfin's DTOs for both the push path and the pull path (`SegmentProvider`), through the facade's servable read. Jellyfin's own segment extraction therefore sees the same data the mirror pushed, and skips rewriting it. Jellyfin persists provider results itself during its own runs, so it can re-add a just-deleted segment from a read that predates the delete, until a later apply converges the item.
- **Locking.** `SegmentChange` holds the item's mutation stripe around the whole apply, so a projection never interleaves with an interactive change or another projection of the same item. Analyzer and maintenance writes take no stripe. The completion deletes a marker only at the version it projected, so work a concurrent write superseded stays pending.
- **Schedule.** A change projects immediately on accept. A poll every `PollInterval` retries due work with exponential backoff, `BackoffBaseSeconds` doubled per attempt and capped at `BackoffMaxSeconds`. Startup recovery tries surviving work once, ignoring recorded backoff. While `UpdateMediaSegments` is off, work sits durably as `ProjectionState.Skipped`, and turning it on replays it. `SegmentChange.ProjectItemsAsync` is the only on-demand entry point, for maintenance code converging the items it touched.

## Per-item disable

An episode or movie can be disabled individually. Its automatic segments are withheld from Jellyfin, and its user segments keep syncing.

- **Output only.** Analysis runs and rows are stored regardless of the flag. The filter lives only in the facade's servable read (`GetServableSegmentsAsync`), which `SegmentDtoFactory` uses for both the push and the pull path. Re-enabling resyncs the untouched rows without re-analysis.
- **Durable toggle.** Toggling commits the flag and its projection work in one transaction. A failed Jellyfin update never rolls the flag back, because the stored flag records the user's intent: the API answers 202 and the journal converges the mirror.
- **Scope.** The flag gates the Jellyfin mirror, the only client-facing read, so third-party clients stop skipping too. Editor reads and analysis reads stay unfiltered, so the editor still shows a disabled item's segments.
- **Storage.** `DisabledItems` holds one row per `ItemId`, and the row's presence is the flag. Cleanup (`CleanItemStateAsync`, shared with the analysis records) prunes rows against the enabled-library inventory, so the flag disappears only when the item leaves the library. Erase and reanalysis leave it alone, like exclusion lists, and rows survive database rebuilds.
- **API.** All dashboard-only and elevation-gated. `GET Intros/DisabledItems/{seasonId}` lists the disabled items Jellyfin shows under a season, by Jellyfin's own season view rule: an in-season special appears under Specials, and under its host season too when Jellyfin's `DisplaySpecialsWithinSeasons` setting is on. `PUT` and `DELETE Intros/DisabledItems/{itemId}` disable and enable one episode or movie, and answer 404 for anything else.
