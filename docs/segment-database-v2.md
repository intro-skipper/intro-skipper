# Segment database v2 - plural segments, tombstones, shared Jellyfin ids

## Context

The original timestamp schema was ported from XML storage: `DbSegment` began with primary key `(ItemId, Type)` - literally one segment per type per episode - and commercials were later patched in via an identity-PK rebuild plus two mutually exclusive filtered unique indexes (`Type = 4` hardcoded in migration SQL). Every layer above branched on `mode == Commercial`. Schema evolution was duplicated between six EF migrations and a hand-rolled raw-SQL repair (`EnsureLegacySchemaCompatibility`) that back-filled `__EFMigrationsHistory`. Jellyfin 12 natively supports any number of media segments per type per item; the one-per-type limit was purely plugin-side (issues #796, #863, #804).

## Decision

Redesign the schema from scratch for the 12.0 major version:

- **New file** `introskipper-v2.db` with a **single EF Core 10 baseline migration**. The legacy `introskipper.db` is read exactly once by `LegacyDatabaseImporter` (read-only connection, shape detection via `pragma_table_info` so repair-era mongrel schemas import too) and is **never modified** - it remains a rollback/downgrade path for pre-v2 plugin versions. The import commits atomically with a `DbImportRecord` marker; the marker, not the file, answers the "was import done" question. Re-importing requires deleting `introskipper-v2.db` and restarting.
- **Uniform plural model**: `Segments` rows are `(Guid Id, ItemId, Type, StartTicks, EndTicks, Source, State, ConfigHash, CreatedAt, UpdatedAt)` with ONE unique index `(ItemId, Type, StartTicks, EndTicks)` for every mode. No commercial special-casing anywhere.
- **Ticks (long)**, matching Jellyfin's `MediaSegment`. Seconds exist only at the analyzer and HTTP edges (`TickConversions`); the old 0.001-second epsilon matching is gone - equality is exact.
- **Shared ids**: `Id` is a client-generated Guid v7 pushed as Jellyfin's `MediaSegment.Id` on sync, so both databases address the same segment by the same Guid (verified: Jellyfin's `MediaSegmentManager` preserves provider-supplied ids; `[DatabaseGenerated(Identity)]` Guids only auto-generate when unset). Unchanged-boundary automatic rows keep their ids across re-analysis. The dependency is deliberately narrow: bulk replace/cleanup is always scoped by the provider id, never the shared Guid, and every correlated delete converges through the per-item replace, which pushes current truth regardless of what ids Jellyfin holds - an id-preservation regression in a future server self-heals silently. (The pre-cutover targeted delete doubled as a loud per-delete canary for that regression; the canary was retired with it, a deliberate observability trade for one write path.)
- **Provenance** (`SegmentSource`: Unknown/Chapter/Chromaprint/BlackFrame/CreditsDerived/User) replaces the `IsUserProvided` bool. `Unknown` can only originate from legacy import.
- **Tombstones** (`SegmentState.Suppressed`): deleting an automatic segment keeps the row, hidden from all normal reads and never synced, and blocks re-insertion of any strictly overlapping automatic segment of the same item+mode (issue #863). User segments hard-delete. Tombstones survive config-hash cleanup and season reanalysis; explicit erase operations (mode/season/item erase) purge them. `Restore` reactivates one.
- **Plural API**: `Episode/{itemId}/Segments` (GET/POST/PUT/DELETE/Restore, seconds at the edge). The singular `Episode/{id}/Timestamps` and `IntroSkipperSegments` endpoints stay as byte-compatible shims (collapse rule: earliest-start active segment per mode, `LegacyTimestampMapper`); `MediaSegmentsApi` keeps its external wire contract. Three deliberate shim write-side changes (release-note items): the Commercial slot of `POST Episode/{id}/Timestamps` now replaces all stored commercials instead of appending, degenerate slots (end ≤ start) are skipped instead of stored (the response stays 204 for the other slots' sake), and a save whose slots are all empty is a pure no-op (it used to run an empty replace plus a mirror sync, so it incidentally healed a diverged mirror; healing now rides on real mutations and the projection journal). The shim writes through the durable segment-change coordinator like every interactive mutation: all slots commit in one transaction, and a change whose Jellyfin projection does not apply synchronously answers `202 Accepted` (see Durable segment changes) instead of failing.
- **Per-item analysis records**: `AnalyzedItems (ItemId, Type, ConfigHash)`, PK `(ItemId, Type)` - one row per item and mode recording the configuration hash it was last analyzed under, found segments or not. Queue verification settles an item whose record matches the current hash (`Analyzed` with segments, `NoSegments` without) and re-analyzes it otherwise. This replaces the JSON `EpisodeIds` list (plus its season-level `ConfigHash`) on `SeasonStates`, which forced read-modify-write on every partial change and keyed analysis state by the mutable season key; every record mutation is now one statement (`MarkItemsAnalyzedAsync`, `ClearItemAnalysisAsync`, `EraseItemsAsync`, `ResetItemsForReanalysisAsync`, `DeleteSegmentsByModeAsync`). `SeasonStates` keeps only the analyzer action and the settled-reanalysis episode set per `(SeasonId, Type)`. The legacy importer expands the legacy per-season episode lists into records under the season's hash, so upgrading does not re-scan. Known semantic: a record survives the item being excluded, so an un-excluded item with a matching record stays settled; `ExcludedTimestamps/Clear` is the explicit reset. Filesystem-driven item changes (`ItemUpdateType.None`, e.g. a file replaced at the same path keeping its Jellyfin id) invalidate the item's records and fingerprint cache through `ResetItemsForReanalysisAsync` before the next coordinated analysis pass, so a same-id replacement does not stay settled under the old file's analysis.
- **Range check**: `CK_Segments_Range` (`EndTicks > StartTicks AND StartTicks >= 0`) makes end > start a database constraint, not only a facade rule.
- All of the above is one baseline migration (`InitialCreate`); the branch's intermediate migrations were squashed before the first release, so no v2 file predating the baseline exists in the wild (branch testers delete `introskipper-v2.db` once and the legacy import repopulates it).

## Consequences

- Multiple intros/outros/commercials per episode are first-class end-to-end (storage → sync → API → config-page editor); `ChapterAnalyzer` emits every matching commercial chapter. Analyzers themselves still emit a single match for non-commercial modes - an analyzer-quality policy declared per mode in `ChapterAnalyzer.AllowsMultipleMatches` - so plural non-commercial segments come from user edits until an analyzer opts in.
- Analysis writes go through one primitive, `ReplaceAutoSegmentsAsync`, whose admission rules (`AutoSegmentAdmissionPolicy`) gate automatic output only: automation may not contradict recorded human intent (an automatic segment is dropped when it strictly overlaps a tombstone or an active user row of the same item+mode), and automatic credits are dropped when they overlap an active introduction. These are admission rules at the write, not state invariants - overlaps are legal stored state (user writes are unconditional; restore/undo do not re-validate), and the stored state's only invariants are the exact-range unique index and the range check.
- The legacy repair machinery, migration back-fill and epsilon matching are deleted; future schema changes are plain EF migrations on the v2 file.
- Restoring an old `introskipper.db` after v2 exists does not re-import (marker); document "delete `introskipper-v2.db` + restart" in release notes as the supported re-import path. A database rebuild keeps the marker when one exists and writes none otherwise, so a rebuild after a failed startup import leaves the retry (and the legacy data) reachable.
- The plugin's own DB remains the source of truth; Jellyfin's MediaSegments table is a mirror per item (`SyncItemAsync` = replace own rows), with other providers' rows untouched.

## Per-item disable (follow-up, supersedes PR #870)

An item (episode or movie) can be individually disabled: its automatic segments are withheld from Jellyfin while explicitly user-provided rows keep syncing. Reimplements PR #870's settled semantics natively on v2; the abandoned earlier semantics (skipping analysis) stays dropped.

- **Output-only**: analysis runs and rows are stored regardless of the flag. The filter lives solely in the facade's servable read (`GetServableSegmentsAsync`), consumed by `SegmentDtoFactory.CreateAsync` - the single source for the push path (`SyncItemAsync`) and the pull path (`SegmentProvider`) - and by the legacy skip shims. Re-enabling resyncs the untouched rows without re-analysis; toggling either way commits the flag durably with its projection work in one transaction - a failed Jellyfin mirror update never rolls the flag back (the stored flag records the user's intent), the API answers `202 Accepted` with a pending projection, and the journaled work converges the mirror. `Unknown`-source rows from legacy import count as automatic.
- **Serving scope**: the flag gates every client-facing read - the Jellyfin MediaSegments mirror and the legacy `Timestamps`/`IntroSkipperSegments` shims - so third-party clients stop skipping too. Editor reads (the plural segments API, the dashboard) and analysis reads stay unfiltered: the editor still shows a disabled item's stored segments. The plural GET requires elevation like its sibling mutations, so the unfiltered stored view is admin-only; the shims' deprecation notes point playback clients at Jellyfin's native MediaSegments API (which the mirror keeps disable-gated), not at the plural API.
- **Storage**: `DisabledItems` - one row per `ItemId` (the primary key); presence of the row is the flag (part of the baseline migration). `SeasonId` is the season-state key (a movie's own id for movies), rewritten on every disable write so a key gone stale after an item moves seasons heals itself; it exists only to serve the season-scoped listing. Cleanup (`CleanItemStateAsync`, shared with the analysis records) prunes by item ID against the enabled-library inventory - never by the stored key, which may be stale - so the flag survives key drift and disappears only when the item leaves the library. Rows survive database rebuilds.
- **The flag is preference, not analysis state**: erase and reanalysis operations leave it untouched - like exclusion lists, it only disappears when the item does.
- **API** (elevation-gated, dashboard-only): `GET Intros/DisabledItems/{seasonId}` returns the disabled set for the browser listing; `PUT`/`DELETE Intros/DisabledItems/{itemId}` disable/enable by item. Mutations resolve the item (404 unless an episode or movie) and record `SeasonStateKeyResolver.Resolve(item)` as the row's season key server-side, so clients never handle the queue-key conventions. Known residual: the listing reads the stored key, so an in-season special disabled from the season it airs within initially renders as enabled when browsed under "Specials" (toggling from there still works).

## Durable segment changes

A durable path from every segment write to Jellyfin: a committed change can no longer lose its mirror push to a failed write, a process death, or a disabled toggle. Every interactive write surface — the plural segments API, the `MediaSegmentsApi` editor contract, the `Timestamps` shim, and the per-item disable toggle — routes through `ISegmentChange`; the former `MediaSegmentEditorService` (write-then-mirror with rollback compensation) is deleted. Analyzer and maintenance writers keep their direct facade calls but journal too: every facade write that changes an item's servable image (`ReplaceAutoSegmentsAsync`, `CleanStaleAutomaticSegmentsAsync`, `EraseItemsAsync`, `DeleteSegmentsByModeAsync`, `ResetItemsForReanalysisAsync`) enqueues the affected items' projection markers in its own transaction, so the projection worker converges Jellyfin for analysis and maintenance exactly as it does for interactive edits. The former `MediaSegmentRefreshService` push/cleanup paths are deleted with their compensation dances (the analyzer's end-of-season refresh, the entrypoint's requeue-on-refresh-failure, the cache cleanup's double sweep); maintenance endpoints converge synchronously by awaiting `ProjectItemsAsync` over the affected ids and lean on the journal for whatever a pass cannot finish. Release-note item: during re-analysis of a season under changed settings, the config-hash cleanup's journaled deletes now empty the affected items' Jellyfin rows within seconds of the cleanup transaction, ahead of the new detections landing per episode — the old rows previously survived until the deleted end-of-season refresh pushed the whole season at once. Second release-note item: a re-analysis that reproduces identical boundaries journals nothing (kept rows only rewrite bookkeeping the mirror does not carry), so it no longer incidentally repairs Jellyfin-side drift the way the unconditional end-of-season refresh did — a hand-deleted or corrupted Jellyfin row now stays divergent until any journaled change touches the item, an idempotent interactive re-assert re-projects it (`Ignored` intents journal precisely for this), or Jellyfin's own media segment scan pulls current truth through the provider. Pure bookkeeping (analysis records, season state, analyzer actions) journals nothing — it changes nothing Jellyfin serves. There are no single-shot user mutators on the facade: every user write goes through `ApplyChangeAsync`, so nothing outside the facade can write servable state without recording its projection.

The design principle: **the journal stores work, not images**. Replaying stored image snapshots would force the journal to duplicate every single-source mechanism it sits beside (the servable-image policy, the Jellyfin write transaction, the mirror's locking) and could push a stale snapshot over newer truth written by paths that do not journal; re-projecting current truth instead means replays can never go stale, markers coalesce, and every crash window degenerates to one extra idempotent sync.

- **Intent API**: `ISegmentChange.ApplyAsync` takes a closed `SegmentChangeIntent` (add/replace/update/delete/restore/visibility/write-timestamps/editor-delete) and returns a typed outcome — `Accepted` (with affected values and the immediate projection disposition), `Ignored` (the intent already held: the mutation is skipped, but a re-projection is still journaled so retrying an idempotent request heals a diverged mirror - except when the target exists in no state at all, where nothing addressable can have diverged and a 404-style probe journals nothing), or `Rejected` (typed reason; journals nothing). Semantics live in the facade's mutation cores: exact-range rows survive in place keeping their Jellyfin-shared ids, restore re-arms the analysis record and drops the row's `ConfigHash`, and an empty replace set carries delete semantics (automatic rows tombstone). `IIntroSkipperDatabase.ApplyChangeAsync` commits the mutation, its analysis-record bookkeeping and the projection journal in one transaction.
- **Journal** (two tables, same database): `ProjectionQueue` — one version-guarded marker per item meaning "the mirror is behind"; `ProjectionExternalOperations` — durable deletes of validated foreign Jellyfin rows, the only non-recomputable payload. Both survive database rebuilds.
- **Projection = current truth**: applying a marker runs the journaled foreign-row deletes and then `MediaSegmentMirror.SyncItemAsync` — the existing single write path, under its per-item stripes, reading through `SegmentDtoFactory`. Replays can never push a stale image; markers for one item coalesce.
- **Coordinator** (`SegmentChange`, hosted): immediate projection on accept, a 10s poll retrying due work with exponential backoff (5s·2^n, capped at an hour), startup recovery that attempts surviving work once ignoring recorded backoff, and a replay nudge when `UpdateMediaSegments` turns on — while it is off, work sits durably as `Skipped`. The coordinator reads and completes the queue through the facade's `ISegmentProjectionJournal` surface; `ProjectItemsAsync` is the only on-demand entry point (maintenance endpoints converge the items they touched).
- **Transport mapping** (`SegmentChangeHttp`): controllers validate requests and map outcomes to HTTP, nothing more. An `Accepted` change whose projection applied synchronously keeps each endpoint's established response shape; a pending or skipped projection answers `202 Accepted` with a `SegmentChangeAcceptedResponse` (change status, projection status, affected segment DTOs) — the change is committed either way, replacing the old rollback/error reporting. Release-note items: mirror failures that answered 500 or threw now answer 202; while `UpdateMediaSegments` is off, every write's projection is `Skipped`, so all four surfaces answer 202 in that steady state where they used to answer their plain success shapes; and rejection texts are composed intent-side, so the `MediaSegmentsApi` type-mismatch 400 names the canonical Jellyfin type rather than echoing the caller's raw string (the "credits" alias included). `Ignored` maps to each endpoint's idempotent success shape, carrying the already-satisfying values for endpoints that return a DTO. `Rejected` maps absent or foreign-owned targets to 404 and everything else to 400.
- **Editor delete** (`EditorDeleteSegmentIntent`, the single external-delete intent): the legacy `DELETE MediaSegmentsApi/{segmentId}` dispatch decided entirely inside the intent transaction. A plugin row sharing the id is deleted authoritatively (type contradiction rejected, already-suppressed rows idempotently ignored) and its Jellyfin twin's targeted delete is journaled with the row's own shape - the durable record that lets a retry whose sync is still pending answer idempotently instead of re-matching. An uncorrelated id resolves the Jellyfin row lazily (the coordinator hands the facade a resolver, invoked only after the correlated lookup misses, so a correlated dispatch never depends on a Jellyfin read), validates its ownership, and matches the plugin counterpart with the shared `UncorrelatedSegmentMatcher` rule (one tick of tolerance, closest wins, non-commercial mode-wide fallback). Every single-row delete - the plural API's included - journals its target row's operation, and the shape-matched pending-op guard answers any retry of a delete whose sync is still pending before matching runs, so the fallback can never re-claim a segment another request already addressed while its drift heal keeps working even while mirroring is off. Journaled foreign-row deletes are deduplicated on their exact validated shape - a row rewritten under its stable id gets a fresh operation while the superseded one drops harmlessly at apply time - and a delete that finds no plugin counterpart does not clear the item's analysis record: deleting a foreign row says nothing about the plugin's own analysis, and the journaled re-projection reasserts plugin truth without a rescan (the pre-cutover unconditional clear could resurrect a similar segment through re-analysis).
